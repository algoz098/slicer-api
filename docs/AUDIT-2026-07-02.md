## Security

### S1 🔴 Arbitrary file write in the STL endpoint — ⚠️ FIXED with residual
**File:** `node-api/src/services/slicer/stl/stl.class.ts:97-100`; schema at `stl.schema.ts:56`.

> **Validation 2026-07-02:** ✅ Core vulnerability fixed. `stl.class.ts:93-96` now ignores `data.output` entirely and always writes to `path.join(os.tmpdir(), 'orca-<uuid>.gcode')`, matching the 3MF behavior. `data.output` is no longer referenced anywhere in the class.
> **Residual:** `stl.schema.ts:56` still declares `output: Type.Optional(Type.String())` — the field is accepted and silently ignored, which misleads API clients. Remove it from the schema (or document it as deprecated).

```ts
const outputDir = data.output ? path.dirname(data.output) : os.tmpdir()
const outputFilename = data.output ? path.basename(data.output) : `orca-${randomUUID()}.gcode`
const outPath = path.join(outputDir, outputFilename)
```

The client-controlled `output` field fully determines both the output directory **and** the filename. The G-code is then written to that path via `orca.slice({ output: outPath })`. There is no directory restriction.

**Impact proof:** `POST /slicer/stl` with `{"output":"/any/path/file"}` writes/overwrites that file with the generated G-code content.

AGENTS.md §5 itself acknowledges the gap: *"The STL service still accepts `output` but should be handled with care."* — the 3MF service was already fixed (`3mf.class.ts:110-111` ignores `data.output`), the STL one was not. **Fix:** ignore `data.output` as 3MF does, or validate it against an allowed directory.

### S2 🔴 No authentication on any endpoint — ❌ OPEN
**File:** `node-api/src/app.ts:61` plus the absence of hooks.

> **Validation 2026-07-02:** ❌ Not addressed. `grep -rn "authenticate(" node-api/src` still returns zero results, and all 7 tests in `test/security/authentication.test.ts` pass (every endpoint reachable without a token).

`app.use(parseAuthentication())` only *parses* the authentication header; there is **no** auth strategy and no `authenticate` hook on any service (searching for `authenticate(` under `node-api/src` returns zero). All services — `slicer/stl`, `slicer/3mf`, `model-info`, `medias`, `profiles`, `profile-converter` — are fully open.

On its own this may be acceptable if the service runs on a trusted network, but it **amplifies S1 and S3**: any client with network access can write/read arbitrary files.

### S3 🟠 Weak file-read allowlist vulnerable to prefix bypass in `medias` — ✅ FIXED
**File:** `node-api/src/services/medias/medias.class.ts:30-41`

> **Validation 2026-07-02:** ✅ Fixed as recommended. `medias.class.ts:36-39` now compares against `dir + path.sep`, so `/tmpsecret/...` no longer matches `/tmp`. Verified by test run: the API-level bypass proof fails (bypass blocked) while the legitimate `/tmp` file access test still passes.

```ts
const isAllowed = allowedDirs.some(dir => safePath.startsWith(dir))
```

`startsWith` compares a string prefix, not a directory boundary. If one of the allowed directories is `/tmp`, the path `/tmpsecret/password` passes (`"/tmpsecret/password".startsWith("/tmp") === true`). The service then returns the file contents as base64 (`medias.class.ts:49-50`). Combined with S2, this is unauthenticated file read.

**Fix:** compare against `dir + path.sep`, or use `path.relative(dir, safePath)` and reject when the result starts with `..` or is absolute.

## Inconsistencies and logic bugs

### B1 🟠 The `config` field has OPPOSITE precedence between STL and 3MF — ⚠️ FIXED with residual
Same field name, inverted semantics between the two slicing endpoints.

> **Validation 2026-07-02:** ✅ Code fixed. `stl.class.ts:107` now merges `{ ...configOverrides, ...baseOptions }`, so `options` wins over `config` — aligned with 3MF and AGENTS.md.
> **Residual:** the schema documentation was not updated — `stl.schema.ts:41` still reads *"configuracao completa via JSON (tem precedencia sobre options e profiles)"*, which now describes the **opposite** of the actual behavior. Update that comment/description.

- **AGENTS.md §2 / docs:** precedence `options` (highest override) > `3MF` > `config`/`profile` (base) > defaults.
- **3MF — consistent with the docs:** `3mf.class.ts:157-162` places `config` into `profile` (base, applied **before** the 3MF) and `options` as the highest override. The engine confirms this semantics: `OrcaSlicerAddon/src/engine/EngineAPI.cpp:167-181` (`profile`→`profile_settings` applied before the 3MF, `overrides`→`custom_settings` applied after).
- **STL — inverted:** `stl.class.ts:109-111`:
  ```ts
  const finalOptions = { ...baseOptions, ...configOverrides } // config overrides options
  ```
  and the schema `stl.schema.ts:41` documents *"config ... takes precedence over options and profiles"*. That is, in STL `config` is the **highest**-priority override — the opposite of 3MF and of AGENTS.md.

The same `config` JSON produces different results depending on the endpoint. The semantics need to be aligned (STL should most likely follow the 3MF model).

### B2 🟡 `coerceValue` converts IDs with leading zeros despite the comment claiming otherwise — ✅ FIXED
**File:** `node-api/src/services/profile-converter/profile-converter.class.ts:48-52`

> **Validation 2026-07-02:** ✅ Fixed. The regex is now `/^[+-]?(?:0|[1-9]\d*)(?:\.\d+)?$/`, which rejects `"007"`, `"0123"`, `"+007"`, `"00.5"` (kept as strings) while still converting `"0"`, `"0.5"`, `"-3"`, `"42"`. All edge cases verified by direct execution.

```ts
// ... avoid turning IDs with leading zeros into numbers
if (/^[+-]?(?:\d+\.\d+|\d+)$/i.test(s)) {
  const n = Number(s)
  if (!Number.isNaN(n)) return n
}
```

The regex matches `"007"`/`"0123"` and `Number("0123") === 123`. The comment promises to avoid exactly this, but there is no guard for leading zeros. Values such as codes/IDs are silently converted and lose their zeros.

### B3 🟡 3MF never silences logging; leftover empty `finally {}` block — ✅ FIXED
**File:** `node-api/src/services/slicer/3mf/3mf.class.ts:197-210`

> **Validation 2026-07-02:** ✅ Fixed. `3mf.class.ts:198` calls `orca.setLoggingSilenced(true)` before `orca.slice(...)` and the previously empty `finally` (`3mf.class.ts:210-211`) now restores it with `setLoggingSilenced(false)`, matching STL and model-info. (Note: proof test B3-A still "passes" only because its regex no longer matches the fixed code and it falls through to a log-only branch with no assertion — vacuous, not a real failure.)

STL and model-info wrap the call with `setLoggingSilenced(true)`/`false` (`stl.class.ts:122-135`, `model-info.class.ts:98-104`). In 3MF an **empty** `try { ... } finally { }` block was left behind and there is no call to `setLoggingSilenced`. Consequence: 3MF slicing dumps libslic3r logs to stdout/stderr (log pollution and possible leakage of temp-file paths). Behavioral inconsistency between equivalent endpoints.

### B4 🟡 `free_result` for `initialize` disabled with a "TEST ONLY" marker in production — ❌ OPEN
**File:** `OrcaSlicerAddon/bindings/node/src/addon.cc:379-388`

> **Validation 2026-07-02:** ❌ Not addressed. The "TEST ONLY" markers are still present at `addon.cc:379` and `addon.cc:387`; the `free_result` call for `initialize` remains commented out and the suspected double-free remains uninvestigated.

```cpp
// TEST ONLY: temporarily do NOT free the initialize result to avoid suspected double-free in engine/free_result.
// if (g_ffi.free_result) { g_ffi.free_result(&r); }
```

Investigation code left in the production path. Two problems: (a) the result leaks on every `initialize`; (b) it signals an **unresolved double-free** in the engine's `free_result` — and `slice()` **still** calls `free_result` normally (`addon.cc:530`), so if the double-free bug is real it remains exposed on the hot slicing path. Needs closure (fix the engine and re-enable, or document why it is safe).

### B5 🟡 Fragile substring-matching for slicing-error classification — ❌ OPEN
**File:** `node-api/src/services/slicer/3mf/3mf.class.ts:229-298`

> **Validation 2026-07-02:** ❌ Not addressed. The substring-based classification is unchanged; the characterization tests in `3mf.error-classification.test.ts` all pass against the current patterns. Acceptable as a known maintenance risk, but keep it tracked.

Distinguishing 400 (user error) from 500 relies on matching message substrings in English/PT (`"outside"`, `"fora da área"`, `"empty initial layer"`, ...). Any wording change upstream reclassifies the error as a generic 500. This is a maintenance risk, not a current runtime bug — but it depends on messages coming from a submodule that evolves independently.

### B7 🟡 `flush_volumes_matrix`: `headsCount` derived from `flush_multiplier.length` (lower confidence) — ❌ OPEN
**File:** `node-api/src/services/slicer/3mf/3mf.class.ts:172-175`

> **Validation 2026-07-02:** ❌ Not addressed. The `headsCount` derivation from `flush_multiplier.length` is unchanged at `3mf.class.ts:172-175`. Still needs validation against real multi-head data.

`expectedSize = filamentCount² × headsCount`, with `headsCount = Array.isArray(flush_multiplier) ? flush_multiplier.length : 1`. The OrcaSlicer flush matrix has size `n_filaments²`; `flush_multiplier` is normally a scalar (a global multiplier), not a per-head vector. In the common case (scalar) `headsCount=1` and it works; if `flush_multiplier` arrives as an array, the expected size diverges from the real one and a valid matrix may be discarded incorrectly. Requires validation with real data.
